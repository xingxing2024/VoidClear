## 检查内容

MySQL 双 Paper：跨服存入同步与顺序领取、三轮竞争领取数量守恒、同时存入不同物品（含旧页面拒绝后背包守恒及重试）、远端清空后的旧视图领取、清扫掉落物提交后入箱与领取。

Folia SQLite：两个假人相距 4096 格时存入同步、竞争领取、区域掉落物清扫、错误菜单拒绝重载和有效菜单关闭旧视图、自动清空、线程异常与正常停服。

Folia/MySQL 使用相同检查，两种后端另有各 12 轮跨区域竞争存取守恒；报告的端到端 p95 包含固定协议等待与轮询，只是有限负载下的观测，不代表数据库事务耗时或生产吞吐量。

各项结果写入 `platform-results-all.json`（或对应单模式文件），每项包含通过状态或失败堆栈。故意将数量守恒作为断言，已知的多服不安全行为应表现为失败，不能因为能够连上数据库就称为通过。各服完整日志为目录下 `platform.log`。

脚本正常结束会停止由它启动的 Minecraft 服务端；MySQL 为外部测试实例，需要在测试后使用对应端口的 `mysqladmin shutdown` 正常停止，不要停止系统中其他 MySQL 服务。

此测试不涵盖代理服切服、玩家背包跨服同步、数据库断网/断电、Folia 与 MySQL 的组合部署、所有操作的随机并发以及大量玩家负载。

## MySQL 修复实现与限制

修复版将 MySQL 的存入、页面提交和清空统一到数据库事务：先锁定元数据行，读取最新物品，再校验显示页面并写入，提交后才执行地面物品移除或由菜单发放物品。过期页面拒绝整次操作并刷新，玩家背包不应被消耗，可重新点击。各服必须全部升级，不能混跑旧异步写入版；升级前协调停服并备份。

当前实现为同步全箱事务，安全优先但不适合高延迟数据库或高频满箱操作；它会阻塞调用线程。即使设置了连接/读取超时，也不等于低卡顿保证。MySQL 必须使用事务存储引擎（正常新建表为 InnoDB）；不要手工改为 MyISAM。此版仍不提供数据库提交与玩家/世界存档之间的崩溃原子性，提交应答丢失或提交后强杀可能损失物品，不能声称 exactly-once 或断电安全。

额外断言检查：编译后用 `java -ea -cp "<dependency classpath>;target/classes;target/test-classes" net.voidclear.v2.store.TrashMysqlCheck`，仅连接上面固定的隔离端口与数据库，以 `assert_` 前缀检查并发新增、编号和停服不复活旧数据，不属于离线 `check.ps1`。
