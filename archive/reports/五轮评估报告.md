## 一、结论与评分

**总体 8/10。单服 Paper / Folia + SQLite 可以上生产；MySQL 多服只适合低频、小箱子、低延迟数据库。**

这是同类 Bukkit 插件里明显偏上的代码：分层清楚，Folia 线程模型认真，文档对限制说得诚实，自检不是摆设。主要风险在性能上限和几个收尾/配置安全点，不在核心正确性。

| 维度 | 分数 | 说明 |
|---|---|---|
| 架构分层 | 8.5 | `Scheduler / Sweeper / Decide / TrashStore / Settings` 边界干净 |
| 线程与并发 | 8.5 | 全局/区域/玩家三路调度，停用屏障写得细 |
| 数据安全 | 8.0 | revision、InnoDB 检查、失败不截断、提交后不自动回滚 |
| 性能 | 6.0 | MySQL 全箱事务 + 多处 O(n) 热路径 |
| 测试 | 7.5 | 离线自检和真实协议测试都有，但仍有覆盖缺口 |
| 文档 | 8.5 | 对限制的说明罕见地诚实；个别结论略有夸大 |

## 三、做得好的地方

- `Sweeper` 的 `active / stopped / issued / inFlight` 状态机与 `stopAndAwait` 是全文最扎实的部分：分批派发不递归，停用后不再动实体，中断不会提前放弃落库。
- `Scheduler` 通过 `RegionizedServer` 判定 Folia，所有世界对象访问都走正确线程；`TrashStore` 明确不让 Bukkit `ItemStack` 跨线程。
- 垃圾箱的“页面快照 + 提交前校验 + 旧页面拒绝”方向正确；MySQL 用 revision 防 ABA，明显优于旧异步写版本。
- `ConfigMigration` 先严格解析两份配置再落盘，坏 YAML 不会被默认值覆盖；“明写空列表 ≠ 缺键”处理正确。
- 测试不是纯摆设：离线自检 + 真实协议 + Folia/MySQL 专项都有；README/PLATFORMS 主动写明不承诺 exactly-once。
- 注释大多解释“为什么”，而不是复述代码。

## 四、仍然存在的问题（按优先级）

### P1｜MySQL 同步全箱事务会阻塞区域线程和玩家点击（高，性能/可用性）

**位置**

- `TrashStore.java:402-474`（`mysqlWrite`）
- `TrashStore.java:235-288`（`deposit`）
- `TrashStore.java:303-337`（`replacePage`）
- `Sweeper.java:282-286`（每个掉落实体调用一次 `deposit`）
- `TrashListener.java:67`（点击处理持有 `synchronized (plugin.trash())`）
- `Countdown.java:175-180` + `VoidClearPlugin.java:209-226`（自动清空在全局 tick 线程同步跑）

**行为**

MySQL 模式下每次存入/点击/清空都会：开连接、开事务、`SELECT ... FOR UPDATE` 锁元数据行、全表读、全表 `DELETE + INSERT`、提交。清扫一轮有 N 个掉落物就是 N 次全表事务。

更严重的是 `TrashListener` 的点击处理与 `TrashStore` 的所有同步方法共用同一把监视器锁。一次慢事务不仅卡住清扫区域，还会让打开菜单、点击、PAPI 查询一起排队；自动清空还发生在全局 tick 线程上。

**建议**

- 按区块/批次合并存款，一次事务接受多个 `ItemStack`（保留 partial + remainder 语义）。
- 满箱且无可合并堆时先做内存短路，避免为必然失败开事务。
- 数据库故障加熔断/退避，避免每个区块都等 3–5 秒。
- 短期至少把 README 的“会阻塞调用线程”说明升级为“可能卡住整个区域/主线程”。

---

### P2｜大箱子下的 O(n) 热路径（中高，单服也会有）

**位置**

- `TrashStore.java:239-266`（`deposit` 复制整张 map，并逐堆 `deserializeBytes` 做相似匹配）
- `TrashStore.java:216-221`（`itemCount` 反序列化全箱，且每次存入都清缓存）
- `TrashStore.java:565-610`（SQLite `writeDatabase` 每次 flush 全表 `DELETE + INSERT`）
- `TrashListener.java:401-416`（菜单每秒刷新取 `%COUNT%`）
- `Placeholders.java:32`（PAPI 取件数）
- `Decide.java:54-73, 141-168` + `Settings.java:120-132`（每个实体重新拷贝约 8 个名单列表，`worldSection` 还会 `getValues(false)`）

**行为**

`deposit` 对每个掉落实体都复制整张 map，并对每一堆反序列化后做相似匹配；满箱且物品各不相同时是 N×M 次反序列化，而且持有全局锁。菜单心跳、`/vc status`、PAPI 每次取件数也会在缓存失效后重新反序列化全箱；SQLite 每次 flush 重写整张表。规则判定每个实体都重新读配置、拷贝名单，一次大清扫会产生大量短命对象。

**建议**

- 维护增量 `long totalAmount`，让 `itemCount()` 变成 O(1)。
- 为可合并堆建 `Material + ItemMeta` 索引（或序列化字节 hash），避免每收一个掉落实体就扫全箱。
- 菜单信息按钮只在计数/倒计时文本变化时重绘。
- 每轮清扫开始时快照一次规则，而不是每个实体读一次配置。

---

### P3｜`period <= 0` 被静默夹成 1 秒（中，配置安全）

**位置**

- `Sections.java:38-40`：`Math.max(1, settings.rawInt("timer.period", 3600))`
- `Sections.java:54-56`：`Math.max(1, settings.rawInt("trash.clear.period", 7200))`
- `ConfigCheck.java:58-59`：把 `trash.clear.period = 0 → 1` 固化成了期望值

**行为**

`trash.clear.period: 0` 会变成**每秒永久清空垃圾箱**；`timer.period: 0` 会变成**每秒扫一轮**。在 Paper 上 `sweep.batch` 的整批区块是同一 tick 内同步跑完的（见 P7），每秒一轮很容易把主线程打满。

`ConfigMigration` 只校验 `mode` 和 daily 的 `times`，不校验 `period`；整体口径是“坏配置拒绝加载”，这里却静默变成了最危险的合法值。

**建议**

加载和 `/vc reload` 时拒绝非正的 `period`（或至少给自动清空一个 ≥60 秒的下限），不要静默夹。同步把 `ConfigCheck` 的期望改成“拒绝加载”或“夹到下限”。

---

### P4｜损坏物品字节不在启动时校验（中，运维）

**位置**

- `TrashStore.java:163-184`（`loadDatabase`）与 `186-209`（`load`）：只检查 null/空/容量/总量，不检查能否反序列化
- `TrashStore.java:216-221`（`itemCount` 反序列化全部记录）
- 使用方：`TrashListener.java:406`（菜单标题 `%COUNT%`）、`CommandHandler.java:379`（`/vc status`）、`Placeholders.java:32`（PAPI `trash_count`）

**行为**

一条“长度合法但内容损坏”的记录能正常通过启动加载；之后第一次打开菜单、查状态或解析 PAPI 时，`itemCount()` 抛出，表现为“箱子打不开 / 状态查不了 / PAPI 失效”，而不是启动时明确失败。

README 第 141 行“异常或超限数据库记录现在会导致启动明确失败”对这类记录**不成立**。

测试也没有覆盖：`TrashStoreCheck` 和 `TrashSqliteCheck` 存的是 `{1,2,3}` 这类字节，只走 `claim/page/size`，从不调用 `itemCount`。

**建议**

- 加载时逐条 `deserializeBytes`，失败带记录 id 明确报错；或把坏行隔离到旁表，保留其余可用数据。
- 至少补一个“合法长度但坏内容”的自检，覆盖 `itemCount` 和打开菜单的路径。
- 短期修正 README 的表述：“空/超限记录会在启动失败；无法反序列化的记录目前不会”。

### P5｜`pageContents` 页缓存只增不减（中，内存）

**位置**：`TrashListener.java:33`（字段）、`:160`（提交后写入）、`:373-377`（只在渲染到该页且内容失效时移除）

**行为**

每次提交都会把该页的 dense entries 和序列化后的槽位存入 `pageContents`；只有换菜单或清空垃圾箱时才整体 `clear()`。大箱子上浏览/操作过很多页后，这些页会长期留在内存里，最坏接近两份箱内容。它不会导致数据错误，但属于只涨不降的内存占用。

**建议**

改成有界 LRU（例如只保留最近 8 页），或在页面内容变化时主动失效相关页。

### P6｜旧 `trash.yml` 迁移失败后会留下“已关闭的 store”（低中）

**位置**：`VoidClearPlugin.java:324-350`

**行为**

迁移流程在 `trash.close()` 之后执行 `Files.move(trash.yml, trash.yml.migrated)`；如果 move 失败（Windows 文件占用、权限、杀毒软件等），异常被 catch，但 `trash` 仍指向**已经关闭**的 store。插件继续运行，但：

- 新的掉落物 `deposit` 一律返回 false，不再进箱；
- `/vc trash` 里的物品无法领取；
- 重启后因 `trash.size() != 0` 会跳过迁移，旧文件永远不再导入。

此外，迁移中途失败会留下半套新数据，老文件仍保留；这条在四轮报告里已提过，本轮确认仍然存在。迁移成功但 `close()` 落盘失败时，代码也会照常把 `trash.yml` 改名，数据只剩 `.migrated` 文件可人工恢复。

**建议**

- move 失败时重新打开 store（或直接回滚这次迁移），不要继续用已关闭的实例。
- 迁移改成“先写临时库，成功后再切换 + 改名”，失败不留下半套数据。
- 迁移前检查目标库为空、迁移后校验件数后再移动源文件。

### P7｜小项（低，但影响可维护性/使用体验）

- **`sweep.batch` 在 Paper 上不是分帧**：`Scheduler.java:210-248` + `Sweeper.java:169-194`，`onChunk` 在主线程内联执行，默认 600 个区块会在同一个 tick 内跑完，再隔一拍派下一批。数值调大是“集中尖峰”，不是“更快分帧”。README 只写了“调度负载越高”，建议写清楚。
- **窗口外点击不丢物品**：`TrashListener.java:69-86` 对 `rawSlot = -999` 不处理，玩家无法像原版一样点击窗口外把手里的物品丢出去。
- **`/vc history player` 仍是半功能**：`CommandHandler.java:291-319` 接受 `player` 过滤，`HistoryLog.java:85-93` 支持 `player=`/`actor=`，但生产只写 `SWEEP` 汇总，没有任何写入方。README 已注明，建议删掉参数或补审计记录。
- **`/vc status` 与 PAPI 在主线程做全量 `itemCount`**：`CommandHandler.java:379`、`Placeholders.java:32`，与 P2 是同一个根因。
- **菜单 YAML 启动时损坏会让整个插件不启用**：`TrashListener.java:36-41` 与 `TrashMenuConfig.java:41-50`；`/vc reload` 时只是拒绝重载，但首次启动会直接失败，不会回退默认菜单。
- **无用抽象/死代码仍在**：`Scheduler.Listener / changed / closeNow / near / async / delay` 没有生产调用方；`VoidClearPlugin.java:97` 仍注册空监听；`TrashStore.claim` 仅测试使用且 MySQL 下直接抛异常；`ConfigMigration.commit` 的备份分支不可达（`writes` 只包含不存在的文件）。
- **交付与文档卫生**：`交付/` 里仍是旧的 `stash.yml`；README 第 47、240、242 行分别称 reviewed4 / reviewed / reviewed2 为“本轮最终交付”，并存容易拿错包；`pom.xml:16` 编译 1.21.11-SNAPSHOT，而 README 第 4 行承诺 1.21.4+，最低版本未实服覆盖。
- **CI 已跑自检**（`.github/workflows/build.yml` 调用 `check.ps1`），但尚未在远端 runner 实跑；`mvn test` 本身仍是空跑。

## 七、最终判断

**这版可以交付单服 Paper + SQLite。** 代码质量明显高于同类插件平均水平，主要风险集中在 MySQL 性能、满箱 O(n) 和配置安全，而不是核心正确性。

MySQL 多服上线前，请先用小箱子、低延迟数据库和受控玩家量验证，并至少做一次满箱 + 高频点击压测；不要把它当成“配了 MySQL 就能随便扩”的方案。
