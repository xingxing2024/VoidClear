## 一、结论摘要

整体仍是**中上水平**的 Paper/Folia 插件代码。作者对 Folia 线程、库存复制与丢件、停用时交付这些高风险点有清晰认识，并且真的在实现中做了防护；自检体系和 README 的诚实程度在个人插件里很少见。

这轮重读后，最重要的结论不是“性能不够好”，而是：**默认配置对“怪物”的判定漏掉了一批常见敌对生物**，这会直接影响插件核心功能。

| 维度 | 分数 | 说明 |
|---|---|---|
| 架构分层 | 8.5 | 唯一判定处、唯一线程入口、唯一库存真源 |
| 线程与并发 | 8.5 | 全局/区域线程分得清，停用屏障设计到位 |
| 数据安全 | 7.5 | 页面级原子替换很好，但读库截断、迁移和停用菜单有边角 |
| 性能 | 6.5 | 默认 SQLite 全表扫描、万格箱子 O(n) 操作、整表写库 |
| 自检/文档 | 8.5 | 离线自检 + 真实协议双客户端 + 说实话的 README |
| 默认规则覆盖 | 6.5 | `Monster` 判定漏掉 Slime/Ghast/Phantom/Shulker 等 |

## 二、高优先级问题

### 1. 默认配置漏扫一批常见“怪物”（高，核心功能）

**位置**

- `src/main/java/net/voidclear/v2/runtime/Sweeper.java:351-353`
- `src/main/java/net/voidclear/v2/rule/Decide.java:50-52, 66-73, 161-165`
- `src/main/java/net/voidclear/CommandHandler.java:254-257`

**问题**

代码用 `instanceof Monster` 判定“怪物”。但在 Bukkit 1.21.7 的类结构中：

- `Slime`：`Mob + Enemy`
- `MagmaCube`：继承 `Slime`
- `Ghast`：`Flying + Enemy`
- `Phantom`：`Flying + Enemy`
- `Shulker`：`Golem + Colorable + Enemy`

它们都**不实现 `Monster`**。

**后果**

默认 `rule.sweep: [monster]` 下，史莱姆、岩浆怪、恶魂、幻翼、潜影贝全部被保留；`/vc check slime` 也会告诉管理员“保留”。对“定时清理实体”的插件来说，这是会直接影响产品预期的缺口。

**建议**

- 怪物分支改用 `Enemy`，但先判 `Animals`，再判 `Enemy`，避免把 `Hoglin` 这类 `Animals + Enemy` 的怪归错。
- 同步修改：
  - `Sweeper.clearable`
  - `Decide.sweeps(Entity)`
  - `Decide.matched` / `Decide.matches`
  - `Decide.verdict`
  - `CommandHandler.check` 的 `monster` 判定
  - README 中的分类说明
- 行为变化需要写进 README：例如 Shulker/Warden 这类 `Enemy` 会开始被默认清理，需要保留时加入 `keep`。

### 2. 在垃圾箱界面点击自己的背包也会写库（中高，性能）

**位置**

- `src/main/java/net/voidclear/v2/listener/TrashListener.java:86-90`
- `src/main/java/net/voidclear/v2/listener/TrashListener.java:126-137`
- `src/main/java/net/voidclear/v2/store/TrashStore.java:272-305`

**问题**

`TrashListener.click` 对 `raw >= 54` 的点击（玩家自己的背包）也会走 `Transfer` + `commit`；`commit` 无条件调用 `replacePage`，而 `replacePage` 会：

- `new ArrayList<>(items.entrySet())` 复制整个 items map；
- 重排当前页、重新求和；
- 调用 `changed()` 触发后台落库。

**后果**

玩家菜单开着时整理背包、换手、丢弃光标物品，都会让万格共享箱重写一页并排一次全量数据库写。这是无意义 IO，还会清空 `cachedItemCount`，进一步放大问题 3。

**建议**

比较 transfer 前后的 top 物品格：

- 没有变化：只应用玩家背包/光标，跳过 `replacePage` 和 `changed()`；
- 有变化（例如 Shift 存入）：按现有逻辑提交。

---

### 3. `itemCount()` 是 O(n) 反序列化，PAPI/菜单会放大（中高，性能）

**位置**

- `src/main/java/net/voidclear/v2/store/TrashStore.java:187-193`
- `src/main/java/net/voidclear/v2/listener/TrashListener.java:369-384`
- `src/main/java/net/voidclear/Placeholders.java:32`

**问题**

`TrashStore.itemCount()` 每次缓存失效都遍历全部物品并 `ItemStack.deserializeBytes`；而 `changed()` 在每次存款/取款时都会清空缓存。

`%voidclear_trash_count%` 会被计分板每 tick 请求，菜单标题每秒请求。大箱子 + 清扫持续掉落时，主线程或 PAPI 线程可能每秒吃几十毫秒——现有实测中“满箱拒收单次 37.6ms”就是同一类全量扫描。

**建议**

维护一个 `long totalAmount`：

- `deposit` 时加上实际接受的件数；
- `replacePage` 时按页重算或按差量更新；
- `clear` 时减去被删除的件数；
- `itemCount()` 直接返回 O(1)。

这样也顺带降低 PAPI 异步线程反序列化 ItemStack 的线程安全疑问。

---

### 4. 停用/整服 reload 时没关闭已打开的垃圾箱（中高，可能复制物品）

**位置**

- `src/main/java/net/voidclear/VoidClearPlugin.java:112-138`

**问题**

`onDisable` 只停清扫、调度、历史和数据库，没有关闭 `TrashListener` 的菜单。

插件停用后监听器被注销，但自定义 `Inventory` 还开着；玩家此时拿走的物品不会反映到已关闭的 store，重新启用后库里的同一批物品还在，就可能重复领取/复制。Paper 整服 `/reload` 或 PlugMan 类工具下比正常停服更现实。

**建议**

在 `onDisable` 开头增加一个 `trashListener.shutdown()`：

- 把所有 `Menu` 标记 `invalidated`；
- 尽力 `closeInventory()`；
- Folia 上按玩家调度，至少保证 Paper 主线程路径；
- 之后再 `scheduler.shutdown()` / `trash.close()`。

## 三、中优先级问题

### 5. SQLite 每 2 秒全表扫描（确认）

**位置**

- `TrashStore.java:92-100, 103-105`（SQLite 也创建 watcher）
- `TrashStore.java:399-430`（`refreshDatabaseIfSafe`）
- `TrashStore.java:424`（无条件清空 `cachedItemCount`）

`refreshDatabaseIfSafe` 不比较 revision，永远全表读，然后替换内存 items。单服 SQLite 没有第二个写者，这个 watcher 本就不需要；MySQL 则应先：

```java
long revision = readRevision(connection, false);
if (revision == databaseRevision) {
    connection.commit();
    return;
}
```

建议：

- SQLite 不启动 watcher；
- MySQL 先比较 revision；
- 只有内容真变化时才清空计数缓存。

这条和问题 3 叠加最伤：每 2 秒一次全表读 + 计数缓存失效 + PAPI 请求全量反序列化。

### 6. `databaseRevision` 的可见性（并发）

**位置**

- `TrashStore.java:45`（普通 `long` 字段）
- `TrashStore.java:426`（watcher 锁内写）
- `TrashStore.java:442`（writer 锁外读）
- `TrashStore.java:462, 539`（其他写入）

`writeDatabase` 在锁外读取 `databaseRevision`，watcher 在锁内更新；JMM 下可能读到旧值，导致伪冲突和重试，极端时连续 8 次后停止自动重试。

建议：字段加 `volatile`，或把读取放进同步块。

### 7. 心跳仍无异常隔离（确认）

**位置**

- `VoidClearPlugin.java:99`（`scheduler.every(20L, this::beat)`）
- `VoidClearPlugin.java:145-153`（`beat()`）

`beat()` 没有 try/catch；坏物品导致 `itemCount()` / `render()` 抛异常时，Paper/Folia 的重复任务可能被取消或持续刷错误日志，倒计时和菜单刷新会永久停摆。

建议：

- `beat()` 整体包一层 `try/catch`，记录后继续下一拍；
- `itemCount()` 对坏数据跳过并告警，而不是整个抛出去；
- 菜单渲染对单条坏数据做隔离，不要影响其他查看者。

## 四、对首轮评估的修正

1. **`Values.hitsMinute` 不是完全死代码**：`SelfCheck.java:37-38, 94-96` 在用，只是生产路径没有调用方。
2. **点击模拟的 `PLACE_*` 路径没有明显 dupe 洞**：核对服务端 `InventoryClickEvent.getAction()` 的生成逻辑后，不同物品放到已占用格子会生成 `SWAP_WITH_CURSOR`，不是 `PLACE_*`。真正脆弱的是拖拽的 `setCancelled(false)`（`TrashListener.java:94-113`）和问题 2 的无意义写库，建议继续保留实服拖拽回归。
3. **`Sweeper.settleRefused` 的 `issued` 重置**仍是边缘路径问题：正常停用不触发，只在调度器异常拒收时可能提前 `complete()`，优先级较低。

## 五、首轮已提出、仍然成立的问题

- 读库超过 `CAPACITY` / `MAX_BYTES` 时 `break` 静默截断，随后 `writeDatabase` 是整表 `DELETE + INSERT`，会永久丢掉截断的行（`TrashStore.java:136-156, 432-477`）。
- 旧 `trash.yml` 迁移失败会留下半套新库数据，旧文件仍在但下次因 `trash.size() != 0` 不再迁移（`VoidClearPlugin.java:319-345`）。
- MySQL 多服领取重复已被 README 和实服测试承认，但代码没有单实例保护；建议启动时做租约/表锁，或拒绝多服。
- `timer.mode: daily` 的 `timer.times` 没有校验；非法或空列表会在 `Timing.secondsUntil` 静默回退到 `period`（`ConfigMigration.java:54-65` 只校验 `trash.clear`，`Timing.java:27-35` 回退）。
- `/vc history` 实际只写入 `SWEEP`，但 tab 补全提示 `WIPE/DRAIN/TIDY/DEPOSIT/WITHDRAW`，`player` / `actor` 过滤也没有写入方。
- 死代码：`Scheduler.Listener / listen / changed / closeNow / near / async / delay`、`TrashMenuConfig.title()`、`Menu.config`、`VoidClearPlugin.java:97` 的 `scheduler.listen(() -> {})`。
- `Placeholders.java:13` 使用已弃用的 `plugin.getDescription().getVersion()`；建议改用 `getPluginMeta()`。
- `pom.xml:16` 编译使用 `1.21.11-R0.1-SNAPSHOT`，README 却承诺 1.21.4+；建议把 `paper.version` 降到最低支持版本，避免误用新 API。
- 根目录大量 `*.log`、`cp.txt` 等构建产物，`.gitignore` 未覆盖 `*.log`。

## 六、测试与流程

这轮实际跑通了离线自检，说明测试体系是有效的。但仍有两点流程风险：

1. **`mvn test` 是空跑**：项目没有 JUnit，自检入口是普通 `main` + `assert`，必须 `java -ea` 才生效。CI 如果只跑 Maven，会“绿色通过、零测试”。
   - 建议把 `check.ps1` 接进 CI；
   - 或给关键类加一个 JUnit 包装。
2. **集成测试不可复现**：`integration-tests/run.ps1` 依赖同级 `SimpleFly/test-server`、`SimpleFly/integration-tests` 和 `minecraft-fakeplayer-next-master`，换机器跑不起来。
   - 建议固定测试服版本、提供自动准备脚本，或至少把依赖版本写进 `PLATFORMS.md`。
3. **`TrashListener` 是唯一没有离线测试的高风险文件**，其中包含手写库存点击模拟、拖拽和 Shift 存取。建议把 `Transfer` 拆出来，用现有的离线 ItemStack 工具补单元测试，不要只依赖实服回归。

## 七、最终判断

- **单服 Paper + SQLite、箱子规模不大**：这版可以上线，工程质量在中上水平。
- **上线前建议先修**：问题 1（Enemy 判定）、问题 4（停用关菜单）、问题 7（心跳异常隔离）。
- **大规模箱子（几千到一万条）**：O(n) 的 `itemCount`、`deposit` 和整表写库是主要瓶颈，建议做增量计数和堆叠索引。
- **MySQL 多服**：仍不建议，现有代码只保证写冲突不覆盖，不保证并发领取不重复。

优势仍然明确：调度抽象干净、页面级原子提交设计好、自检和实服回归认真、README 对限制的说明诚实。短板集中在“默认规则覆盖”和“大箱子性能”，不是架构层面的失控。
