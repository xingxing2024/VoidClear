## 三、剩余风险（按优先级）

以下问题多数不是“新 bug”，而是当前设计的已知上限；部分已在 README/源码注释里承认。建议按顺序处理。

### 1. MySQL 每次存入/点击都做一次全箱事务（高，性能/可用性）

**位置**

- `TrashStore.java:402-474`（`mysqlWrite`）
- `TrashStore.java:235-288`（`deposit` 包装）
- `TrashStore.java:303-337`（`replacePage` 包装）
- `TrashStore.java:376-394`（`clear` / `clearAll` 包装）
- `Sweeper.java:248-303`（每个掉落实体调用一次 `deposit`）

**行为**

MySQL 模式下，每一次 `deposit` / `replacePage` / `clear` 都会：

1. 打开连接、开启事务；
2. `SELECT ... FOR UPDATE` 锁住元数据行；
3. 全表读取当前箱子；
4. 执行一次内存操作；
5. 全表 `DELETE + INSERT`；
6. 提交；
7. 提交后才执行世界物品移除或玩家发放。

**后果**

- 清扫一轮收集 N 个掉落物，就是 N 次全表读 + N 次全表写 + N 次提交；不是 N 个物品一次事务。
- 即使箱子已满、`deposit` 最终返回 false，也会先完成一次全表读取事务。
- 数据库断网/变慢时，`connectTimeout` 3 秒、`socketTimeout` 5 秒会直接阻塞调用它的区域线程/玩家线程；每个区块至少一次，可能造成大面积卡顿。
- 因为 `mysqlWrite` 在 `synchronized` 方法内执行，事务期间会持有 `TrashStore` 监视器；PAPI、菜单 `itemCount()`、`/vc status` 也会被一起阻塞。

**评价**

这是为了“多服领取守恒”做出的正确性取舍，源码第 403 行的 `shortcut:` 注释和 README 第 135 行、`PLATFORMS.md` 第 31 行都承认了“同步全箱事务会阻塞调用线程”。所以它不算隐瞒，但它是当前**最大的扩展性上限**。

**建议**

- 清扫路径按区块/批次合并存款：一次事务接受多个 `ItemStack`，再统一执行世界移除（注意部分接受和 remainder 语义）。
- 对“箱子已满且没有可合并堆”的情况加一个内存短路，避免为必然失败的操作开事务；要接受远程服务器可能刚释放空间的事实。
- 数据库故障时加熔断/退避，避免每个区块都等 3 秒。
- 长期方案：行级 upsert + 预占/领取记录，而不是每次全表重写。

### 2. MySQL watcher 仍然每 2 秒全表扫描，且不比较 revision（高，空闲负载）

**位置**

- `TrashStore.java:96-106`（MySQL watcher 每 2 秒）
- `TrashStore.java:527-559`（`refreshDatabaseIfSafe`）
- `TrashStore.java:537` 读取 `revision`，但后续没有提前返回
- `TrashStore.java:553` 无条件 `cachedItemCount = null`

**行为**

即使数据库没有任何变化，MySQL 模式也会每 2 秒：

- 全表读取所有 `item_data`；
- `copyInto` 克隆整份字节数据；
- 替换内存 `items`；
- 清空物品件数缓存。

满箱 1 万条、接近 64 MiB 时，这是持续的网络、磁盘和 GC 成本；清空缓存还会让下一次 PAPI/菜单查询重新反序列化全部物品（见问题 3）。

**建议**

在读取完整表之前先比较 revision：

```java
long revision = readRevision(connection, false);
if (revision == databaseRevision) {
    connection.commit();
    return;
}
```

如果内容确实变化，再读取物品；只有内容变化时才清 `cachedItemCount`。这是当前**改动最小、收益最大**的剩余优化。

---

### 3. `itemCount()` 仍是 O(n) 反序列化，PAPI/菜单会放大（中高）

**位置**

- `TrashStore.java:216-221`（逐个 `ItemStack.deserializeBytes`）
- `TrashListener.java:401-416`（`titleValues` 每次都取 `%COUNT%`）
- `Placeholders.java:32`（`%voidclear_trash_count%`）

**行为**

- 每次 `changed()`、MySQL 事务、MySQL watcher 刷新都会清空缓存；
- 下一次 `itemCount()` 会反序列化全部物品；
- 满箱时一次全量扫描约 37.6 ms（README 已记录）；
- 计分板每 tick 请求、菜单每秒刷新时，这个成本会被放大。

MySQL 下尤其明显：一次清扫可能触发多次事务，每次事务清空缓存；如果 PAPI 计分板每 tick 请求，主线程可能反复吃几十毫秒。

**建议**

维护一个 `long totalAmount`，在 `deposit` / `replacePage` / `clear` 时按实际接受/删除的件数增量更新；`itemCount()` 变成 O(1)。菜单按钮也只在计数或倒计时文本变化时重绘，而不是每秒无条件重建。

---

### 4. `deposit` / `replacePage` 的 O(n) 内存操作（中高，单服大箱子）

**位置**

- `TrashStore.java:239-266`（`proposed.putAll(items)` + 逐堆反序列化）
- `TrashStore.java:309-336`（整张 map 复制、重排、求和）

**行为**

- `deposit` 每收一个掉落实体，都要复制整张 map，并逐个反序列化已有堆叠来寻找可合并项；
- 满箱时这个扫描仍然发生，单次约 37.6 ms；
- `replacePage` 每次点击都复制整张 map、重建结果、求和。

**后果**

单服 SQLite 下，满箱 + 大量掉落/频繁点击会明显卡顿；MySQL 下还会叠加问题 1 的全表事务。

**建议**

- 增加按 `Material + ItemMeta` 哈希的可合并堆索引，只扫描有空间的堆；
- 或至少限制每轮 `deposit` 的扫描量，剩余下一轮处理；
- 长期把“页”做成独立结构，`replacePage` 只改本页而不是复制全表。

---

### 5. MySQL 提交后的世界/背包动作存在“结果不明”窗口（中，已承认）

**位置**

- `TrashStore.java:451-453`（提交后执行 `committedEffects`）
- `TrashStore.java:469-472`（提交后失败只报错、不回滚）
- `TrashMysqlCheck.java`（提交后异常断言）

**行为**

- 存入：数据库已提交，但此后世界物品移除失败/进程被杀 → 箱内和地上各一份；
- 取出：数据库已删除，但玩家背包发放前进程被杀 → 玩家没拿到；
- `socketTimeout` 导致提交应答丢失时，代码只能按“未确认”处理，无法知道数据库是否真的提交。

README 第 135 行和 `PLATFORMS.md` 第 31 行已经明确说“不承诺 exactly-once、断电可能丢物品”，`TrashMysqlCheck` 也测了提交后回调故障。这是分布式一致性限制，不是简单的代码遗漏。

**建议**

- README 把“存入可能重复、取出可能丢失”两种情况分别写清楚，而不只是“可能丢失”；
- 如果要进一步收紧，需要引入 pending/操作日志表和可恢复的重放/对账，不适合在当前版本硬塞。

### 6. 旧 `trash.yml` 迁移失败会留下半套数据（低）

**位置**

- `VoidClearPlugin.java:324-350`

迁移中途失败时，新数据库里已经写入一部分条目，旧 `trash.yml` 仍保留；下次启动因为 `trash.size() != 0` 会跳过迁移，剩余旧物品永远迁不过去。

**建议**：失败时清空新库（或写迁移标记）以便重试；或先迁移到临时表，成功后再切换。

## 五、最终判断

**这版可以交付。** 上一轮的结构性问题已经处理到位，最终 JAR 与文档、验证记录一致，单服 Paper + SQLite 没有明显阻塞上线的问题。

如果要给下一轮排优先级：

1. MySQL 同步全箱事务的批量化/熔断（问题 1）；
2. MySQL watcher 的 revision 短路（问题 2）；
3. `itemCount` 增量化（问题 3）；
4. `deposit` 的堆叠索引（问题 4）；
5. 迁移、daily 校验、history、交付目录等收尾（问题 6–9）。

前两项是“改动小、收益大”；第三、四项需要一点设计；第五项的 MySQL 提交模糊窗口属于分布式一致性取舍，建议只补文档，不建议在当前架构里硬做 exactly-once。
