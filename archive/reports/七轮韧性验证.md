## 安全范围

- 正式插件仍使用第六轮交付 `target/VoidClear-3.0.0-reviewed6-release.jar`，本轮尚未改生产源码，不覆盖已交付包。
- 修改前备份已逐条读取验证（65 项），SHA256 `F5688A239C235D453A7CD89ED335DCD5E983DADF9B40839958FCCCDE52E289B9`。
- 测试服目录 `target/platform-tests/resilience-*`，回环端口 25657；隔离 MySQL 仍为 127.0.0.1:33317、`voidclear_test`。TCP 转发故障端口 33318，独立 `faultprobe_` 前缀；测试服使用既有隔离 `platform_` 前缀。不得在测试运行时并行执行其他共享此测试前缀的脚本。
- 强杀仅针对本脚本直接 spawn 返回的 Java 子进程句柄，不搜索/终止外部 PID，不停止系统原有 mysql 服务。测试脚本会正常停止其余子服与转发器；外层 PowerShell 在 finally 关闭独立数据库。

## 新验证入口

先用原 `run.ps1` 中 javac/jar 步骤构建最新 Probe，不要重新打包或替换已交付生产 JAR。启动独立 MySQL，再设置：

```powershell
$env:VOIDCLEAR_TEST_JAR='../target/VoidClear-3.0.0-reviewed6-release.jar'
node integration-tests/resilience.cjs
```

结果 `integration-tests/resilience-results.json`，每个场景服务端日志位于对应测试服的 `platform.log`。需要同级 SimpleFly 运行时/协议依赖和既有 PAPI 文件，仍不是完全独立可移植测试包。

1. 每方向 30 ms 的 TCP 转发延迟，真实 ItemStack deposit，记录调用线程实际耗时与件数。
2. 独立连接持有元数据行锁 1500 ms，检验释放后存入守恒，同时报告同步等待。
3. 初始化成功后关闭转发监听及已有连接，要求后续操作拒绝、不执行交付、数据库和内存仍为原数量。这里只是操作前连接拒绝，不冒充 COMMIT 已执行但 ACK 丢失的测试。
4. SQLite、MySQL 各至少五分钟、不少于 100 轮，两真实协议客户端竞争领取；每轮核验箱子和两背包总量，再清理本轮已领取测试物品。耗时包括协议等待，不是数据库延迟。此规模不是生产长期或高并发压力。
5. 两后端分别对存入/领取做保存后、未保存后强杀进程再启。基线先 player.saveData + SQLite writer barrier；操作确认后立刻强杀，或再次显式保存后强杀。保存后要求总量 16；未保存场景逐项记录恢复后的箱子、玩家数量和总量差，不把已知丢失/重复标成 exactly-once 通过。

## 判断边界

进程强杀不等于断电：操作系统和 MySQL 实例仍运行，没有模拟掉电、磁盘满、文件系统损坏或数据库进程崩溃。同步 MySQL 预计会暴露主线程阻塞，这个问题不会因为数量守恒而消失。玩家存档与数据库是两个提交域，不能通过自动按旧快照补发修复崩溃差异，也不能为提高分数直接引入重试。

## 实测结果

测试于 2026-11-07 完成，原始结果 `integration-tests/resilience-results.json` 保留不改写。运行脚本完成不等于安全验收通过：原脚本将未保存崩溃场景记为观察，因此当次退出成功；现已改为完成全部观察后，发现数量不守恒即退出非零，不能把观察完成伪装成安全通过。

| 场景 | 结果 |
| --- | --- |
| TCP 每方向注入 30 ms | 存入调用耗时 961.57 ms，数量正确，但明显阻塞调用线程 |
| 元数据行锁持有 1500 ms | 存入调用耗时 1534.88 ms，数量正确，同步等待被证实 |
| 操作前连接拒绝 | 3.16 ms 拒绝，无交付，数据库和内存数量不变；未覆盖 COMMIT ACK 丢失 |

## 不做危险的“假修复”

不能在失败后自动恢复旧页、重新发物品或仅把 saveData 放到数据库提交后就宣称完成修复。真实解决需要可恢复交付协议：持久化交易状态、玩家侧可核验交付身份、隔离未确认交易并拒绝重复消费，以及重启核对；存入、取出、拖拽、光标、副手、掉落物和跨服竞争都必须纳入。异步化 MySQL 则需预留/确认与玩家/区域线程调度协议，不能把 Bukkit 背包操作直接扔进异步线程。

### 清扫保存后对照的屏障错误

两个清扫 `saveAfter=true` 原始记录也为32，但日志显示 `VC_SAVEWORLD_after` **先于**服务器 `Saving the game`，之后没有 `Saved the game` 就被强杀：Probe 的 `dispatchCommand` 返回只是把原版命令排队，并不是落盘完成。不能据此认定“save-all flush 完成仍重复”。基线保存则日志显示完成后才执行清扫，因此未保存场景的重复证据仍成立。

已把探针标记改名为 `VC_SAVEWORLD_QUEUED_`，脚本另等服务器实际 `Saved the game` 后才继续。保存屏障、延迟下界和配置读回校验进入定向复跑（`node integration-tests/resilience.cjs focused`）；该模式只覆盖故障及4项清扫观察，不替代整套12项或五分钟负载。结果按启动时间独立保存。
