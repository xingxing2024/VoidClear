## 一、结论

**总体 8/10。单服 Paper + SQLite 可以上线；MySQL 多服只适合低频、小箱子、低延迟数据库。**

这是同类 Bukkit 插件里少见的成熟代码：分层清楚，Folia 线程模型认真，文档对限制说得诚实，自检不是摆设。但仍有一处结构性性能上限（MySQL 同步全箱事务）和若干"看起来能用、实际半功能"的收尾问题。

| 维度 | 分数 | 说明 |
|---|---|---|
| 架构分层 | 8.5 | `Scheduler / Sweeper / Decide / TrashStore / Settings` 边界干净 |
| 线程与并发 | 8.5 | 全局/区域/玩家三路调度与停用屏障写得细 |
| 数据安全 | 8.0 | revision、InnoDB 检查、失败不截断、提交后不自动回滚 |
| 性能 | 6.0 | MySQL 全箱事务 + 多处 O(n) 热路径 |
| 测试 | 7.5 | 自检覆盖不错，但 `mvn test` 空跑、CI 不跑自检 |
| 文档 | 9.0 | 对限制的说明罕见地诚实 |

## 三、做得好的地方

- `Sweeper` 的 `active / stopped / issued / inFlight` 状态机与 `stopAndAwait` 是全文最扎实的部分：分批派发不递归，停用后不再动实体，中断不会提前放弃落库。
- `Scheduler` 通过 `RegionizedServer` 判定 Folia，所有世界对象访问都走正确线程；`TrashStore` 明确不让 Bukkit `ItemStack` 跨线程。
- 垃圾箱的"页面快照 + 提交前校验 + 旧页面拒绝"方向正确；MySQL 用 revision 防 ABA，明显优于旧异步写版本。
- `ConfigMigration` 先严格解析两份配置再落盘，坏 YAML 不会被默认值覆盖；"明写空列表 ≠ 缺键"处理正确。
- 测试不是纯摆设：离线自检 + 真实协议 + Folia/MySQL 专项，README/PLATFORMS 主动写明不承诺 exactly-once。
- 注释大多解释"为什么"，而不是复述代码。

## 四、仍然存在的问题（按优先级）

### P1｜MySQL 同步全箱事务会阻塞区域线程和玩家点击（高，性能/可用性）

**位置**

- `TrashStore.java:402-474`（`mysqlWrite`）
- `TrashStore.java:235-288`（`deposit`）
- `TrashStore.java:303-337`（`replacePage`）
- `Sweeper.java:282-286`（每个掉落实体调用一次 `deposit`）
- `TrashListener.java:67`（点击处理 `synchronized (plugin.trash())`）
- `Countdown.java:175-180` + `VoidClearPlugin.java:209-219`（自动清空在全局 tick 线程同步跑）

**行为**

MySQL 模式下每次存入/点击/清空都会：开连接、开事务、`SELECT ... FOR UPDATE` 锁元数据行、全表读、全表 `DELETE + INSERT`、提交。清扫一轮有 N 个掉落物就是 N 次全表事务。

更严重的是 `TrashListener` 的点击处理与 `TrashStore` 的所有同步方法共用同一把监视器锁。一次慢事务不仅卡住清扫区域，还会让打开菜单、点击、PAPI 查询一起排队；自动清空还发生在全局 tick 线程上。

**建议**

- 按区块/批次合并存款，一次事务接受多个 `ItemStack`（保留 partial + remainder 语义）。
- 满箱且无可合并堆时先做内存短路，避免为必然失败开事务。
- 数据库故障加熔断/退避，避免每个区块都等 3–5 秒。
- 短期至少把 README 的"会阻塞调用线程"说明升级为"可能卡住整个区域/主线程"。

---

### P2｜MySQL watcher 每 2 秒全表读，revision 读了但没用（中高，改动小收益大）

**位置**：`TrashStore.java:527-559`

**行为**：即使数据库完全没有变化，也每 2 秒全表读取所有 `item_data`、`copyInto` 克隆整份字节、替换内存并清空件数缓存。满箱接近 64 MiB 时是持续的网络、磁盘和 GC 成本。

**建议**：读完 revision 后先比较，相同就直接返回：

```java
long revision = readRevision(connection, false);
if (revision == databaseRevision) {
    connection.commit();
    return;
}
```

这是三轮报告问题 2，当前源码仍未修。

---

### P3｜O(n) 热路径（中高，单服大箱子）

**位置**

- `TrashStore.java:216-221`（`itemCount` 反序列化全箱）
- `TrashStore.java:239-266`（`deposit` 复制整张 map 并逐堆反序列化）
- `TrashStore.java:309-336`（`replacePage` 复制、重排、求和）
- `TrashListener.java:401-416`（菜单每秒刷新取 `%COUNT%`）
- `Placeholders.java:32`（PAPI 取件数）

**建议**

- 维护增量 `long totalAmount`，在存入/取出/清空时按实际数量更新，`itemCount()` 变 O(1)。
- 为可合并堆建 `Material + ItemMeta` 索引（或直接按序列化字节 hash），避免每次存一个掉落实体都扫全箱。
- 菜单按钮只在计数或倒计时文本变化时重绘，而不是每秒无条件重建。

---

### P4｜`/vc history` 的筛选项是"半功能"（中，功能/文档不一致）

**位置**

- `VoidClearPlugin.java:247-255`：生产只写 `SWEEP` 记录。
- `CommandHandler.java:432`：tab 补全提示 `WIPE / DRAIN / TIDY / DEPOSIT / WITHDRAW`。
- `HistoryLog.java:85-93`：支持 `player=` / `actor=` 过滤，但没有任何写入方。
- README 第 63 行与 `messages.yml:69-70` 把筛选描述成可用功能。

**后果**：管理员按 tab 选择这些类型或按玩家筛选，永远得到"暂无记录"，容易误判为"没有操作"。

**建议**：二选一——补上存入/取出/清空的 `actor=` 记录，或删掉未实现的类型、筛选参数和文档描述。

---

### P5｜`timer.times` 未校验，坏配置会静默退回 interval（中低）

**位置**

- `ConfigMigration.java:54-65`：只校验 `trash.clear`。
- `Timing.java:27-35`：非法或空时刻时回退到 `period`，无日志。
- `Sections.java:46-48`：`timer.times` 直接读原始列表。

**后果**：`timer.mode: daily` 但时刻写错/为空时，插件不报错、不拒绝加载，静默按 interval 跑，和"坏配置拒绝加载"的整体口径不一致。

**建议**：与 `trash.clear.times` 统一校验；至少在回退时打 WARNING。

---

### P6｜旧 `trash.yml` 迁移失败会留半套数据（低）

**位置**：`VoidClearPlugin.java:324-350`

迁移中途失败时，新数据库已写入一部分，旧文件仍保留；下次启动因为 `trash.size() != 0` 会跳过迁移，剩余旧物品永远迁不过去。

**建议**：失败时清空新库或写迁移标记；或先迁到临时表，成功后再切换。

---

### P7｜Sweeper 最后一批全被拒收时可能永久 active（低，但测试在掩盖）

**位置**

- `Sweeper.java:227-231`（`settleRefused`）
- `SweeperCheck.java:524-525`（测试手动 `settle()` 才通过）

**行为**：最后一批区块全部被调度器拒收、且 `later()` 返回 true 时，`settleRefused` 没有减 `issued`，下一次 `issue()` 又因队列为空直接返回，本轮永远不会触发 `complete()`，`active` 保持为 true。

生产里 `onChunk` 返回 false 基本只在停用边界出现，风险低；但自检用手动 `settle()` 让它过去，等于没有验证产品路径。

**建议**：让 `settleRefused` 显式结掉被拒的份额，并在队列为空时收尾；测试改为验证产品代码自愈。

---

### P8｜杂项（低，但影响可维护性）

- **坏 blob 的失败时机不明确**：启动只校验非空/容量，不校验能否反序列化（`TrashStore.java:163-184`）。单条数据损坏会让 `itemCount()` 或打开菜单时才抛错，表现为"箱子打不开"，而不是启动时明确失败。
- **无用抽象/死代码**：
  - `VoidClearPlugin.java:97` 注册了一个空监听 `scheduler.listen(() -> { })`。
  - `Scheduler.Listener / changed / closeNow / near / async / delay` 当前没有实际调用方。
  - `Settings.java:93-98` 的三参 `raw` 重载无人使用。
  - `TrashStore.claim` 仅测试使用，且 MySQL 下直接抛异常。
  - `ConfigMigration.commit` 的备份分支不可达：`writes` 只会包含不存在的文件。
- **CI 不跑自检**：`.github/workflows/build.yml` 只执行 `mvn package`，而 `mvn test` 是空跑；`check.ps1` 只在本地生效。
- **交付目录仍是旧的**：`交付/` 里只有旧的 `stash.yml`，最终 JAR 只存在于被 gitignore 的 `target/`。
- **版本/API 小问题**：`pom.xml:16` 编译 1.21.11，README 承诺 1.21.4+；`Placeholders.java:13` 仍用已弃用的 `getDescription()`。

## 七、最终判断

**这版可以交付单服 Paper + SQLite。** 代码质量明显高于同类插件平均水平，主要风险集中在 MySQL 性能和几个半功能/收尾点，而不是核心正确性。

MySQL 多服上线前，请先用小箱子、低延迟数据库和受控玩家量验证；不要把它当成"配了 MySQL 就能随便扩"的方案。
