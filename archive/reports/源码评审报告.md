## 零、先说结论

**这是一份中上水平的 Paper/Folia 插件源码。**

作者很清楚这类插件最危险的地方在哪（Folia 线程、库存复制/丢件、停用时的交付），而且真的在防，

## 一、做得好的地方（建议保留，别为了“简洁”砍掉）

### 1. 线程模型是这份代码的核心价值

- `Scheduler.global()` 只把 `Bukkit.isPrimaryThread()` 这一句放进 try，
  **任务本身不在 try 里**，避免“任务抛异常被当成 Folia 抛出而重排一次、跑两遍”。
  这个细节绝大多数开发者会写错。
- 清扫按区块派任务（`onChunk`），而不是按实体，区域并行粒度和 Folia 的模型对得上。
- 停用屏障 `Sweeper.stopAndAwait` 等的是 `inFlight`（正在交付的区块），
  不是调度队列。**等队列会等死**，这是踩过坑才写得出的设计。

### 2. 库存的原子性

- `Stash.takeInto` 在库存锁里同时做三件事：核对 `revision`、塞背包、扣库存。
  杜绝了“取出来了但塞不回去”和“旧界面按旧页码取新列表”两类丢件/错件。
- `StashCheck` 里有两个玩家持同一 `revision` 并发取同一格，断言只有一个成功，另一个拿到 `STALE`。
  这是**真正验证了锁内核对**的测试，不是摆样子。
- `flush()` 用 `AtomicBoolean` 保证同一时刻最多一个快照在写，
  配合 `UiChecks` 的“连续 10 次 flush 只入队一次”，把异步落库积压问题堵住了。

### 3. 配置读取的三层语义

`rawListSet` 明确区分了三种状态：

- 用户**明写了**（含 `[]` 空表）→ 照用用户的；
- 用户**没写但 jar 默认有** → 用 jar 默认；
- **都没有** → 用代码兜底。

并且三份配置文件**全部读完才发布**新配置，任何一份 YAML 坏了都整体拒绝，
不会出现“config 换了 messages 没换”的中间态。`ConfigCheck` 覆盖了这几种情况。

### 4. 异常隔离

`Sweeper.sweep` 的 `finally` 里交付已移除的掉落物：某个实体抛异常，
前面已经 `remove()` 的东西照样进拾遗站，不会因为异常变成“吞物品”。
`Verify` 用代理实体注入异常验证了这一点。

### 5. 自检体系

没有 JUnit，但 `check.ps1` 一条命令跑通 5 个入口，另有独立 Paper 实服回归
（SQLite 往返、重启恢复、异常注入、阻塞数据库、坏配置重载、Folia 不建 GUI）。
这种“宁可写丑脚本也要能验证”的做法，在个人插件里很少见，值得肯定。

## 二、必须修的问题

### P0：Folia 上库存会在无法领取的情况下被定时烧掉

**现象**：`StashScreen.open()` 在 Folia 上直接拒绝打开界面，
但 `SweepGuardPlugin.beginWipe()` 照常按 `stash.wipe-period` 执行 `stash.drain()`，
库存被清空且玩家从未有机会领取。

**现状**：README 第 5–6 行有一句话提示“如果计划迁至 Paper 领取，请在倾倒期限前正常停服并迁移”，
但：

- `config.yml` 里 `stash.wipe-period` 没有任何警告；
- `/sg status` 不会提示“当前 Folia，库存会被无条件倾倒”；
- 启动日志只有一条 `WARNING` 说 GUI 不开放，没有说库存会丢。

**建议**（任选其一，按工作量从小到大）：

1. 启动时在 Folia 上对 `stash.enable: true` 打 `SEVERE` 级别日志，明确写“库存将在 X 秒后被清空且玩家无法领取”。
2. Folia 上 `stash.enable` 默认视为 `false`，需要服主显式打开。
3. Folia 上跳过 `beginWipe`，只保留手动 `/sg wipe`。

### P0：`beginSweep()` 每次到点清扫会播报两条一模一样的“清扫开始”

**位置**：`SweepGuardPlugin.java:265-274`

```java
private void beginSweep() {
    broadcast(message("sweep.countdown.start", "&a清扫开始。"));   // 第一条
    sweepTimer.ring(...);
    runSweep(message("sweep.triggered", "&7清扫已开始。"), ...);  // runSweep 内部又 broadcast 第二条
}
```

`runSweep` 内部会 `broadcast(startLine)`，所以玩家会连续收到
`sweep.countdown.start` 和 `sweep.triggered` 两句话。

**建议**：`beginSweep` 只保留 `ring`，播报交给 `runSweep` 统一处理；
或者 `runSweep` 增加一个 `boolean announce` 参数。

### P1：`sweep.floor` 代码默认值与模板不一致

- `Sections.Pace.floor()` 默认返回 **400**；
- `config.yml` 写的是 `floor: 0`（关闭）。

服主删掉这个键后，会意外落到“区块里少于 400 个待清对象就整块跳过”，
和模板行为完全不同，且没有任何提示。

**建议**：把代码默认也改成 `0`（改模板更麻烦，也不解决“删键”场景）。

### P1：Folia 禁 GUI 后，`StashListener` 仍保留半套逻辑

`StashScreen.owns()` 仍然按 `Holder` 判断，`StashListener` 仍然注册。
如果将来有别的插件或代码路径让玩家打开一份本插件的界面，
`liveOf` 会因为 Folia 没有登记而返回 `null`，`onDrop` / `onPickup` 会误拦截。

**建议**：`Scheduler.folia()` 为 true 时，`onEnable` 里不注册 `StashListener`；
或在 `owns()` 里加 `stash.scheduler().folia()` 短路返回 false。

### P1：`CareListener.onExplode` 注释与实现不符

注释现在只剩“把苦力怕挪到地面……”的历史描述，但相关代码已经删了，
实际只做 `blockList().clear()` 和 `setYield(0)`。
同时 `onPhysical` 里“只认玩家自己踩”的注释也容易让人误以为怪物踩踏不拦——
实际上怪物踩踏走 `EntityChangeBlockEvent`，两个事件分工要写清楚。

**建议**：更新注释，或在 `onPhysical` 里补一句“怪物路径见 onTrample”。

## 三、值得考虑（不阻塞发布）

### 1. MySQL 单服的运行时约束

落库是“事务内清表再整批写”，两个服连同一个库会互相覆盖。
README 写了“仅单服”，但代码没有任何运行时检测。

可选做法（任选，成本递增）：

- 启动时打一条 `WARNING`：“MySQL 后端仅支持单服，多服共用会互相覆盖”；
- 表名加实例标识（`stash_item_<instance>`）；
- 写入前用行版本号做乐观锁。

### 2. `Scheduler` 接口方法偏多

当前主线真正用到的是 `global / once / later / onChunk / every / playerNextTick`；
`near / async / delay / player` 目前没有调用方。
多一个接口方法就多一个测试面和维护面，可以考虑删或标注 `shortcut:`。

### 3. `Verify` 的测试污染风险

`UiChecks` 里 `plugin.stash().drain()` 之后才 `accept(original)`，
如果中途抛异常，库存会变空，`Verify` 第二次跑会卡在 `total(sg) == 90`。
建议把这段操作放进 `try/finally`。

### 4. `README` 与代码的“入口数”描述

`check.ps1` 跑了 5 个入口，README 表格也是 5 行，但其中 `StashCheck` 一行没提新增的
并发/停用测试，`SweeperCheck` 一行提了。建议补齐或统一。

## 四、可以忽略 / 属于设计选择

以下几处看着像问题，但评审认为**不需要改**：

- `Decide.matched` 和 `Decide.matches` 逻辑重复：一个走实体对象、一个走纯字段，
  为 `/sg check` 这条不会影响实体的查询路径服务，拆开是合理的。
- `Grid` 空布局回退“整页可放”：注释里已经标了 `shortcut`，也能避免东西藏起来找不到。
- 没有 JUnit：对插件项目来说，`check.ps1` + 实服回归已经够用。
- `FakeItem` 用 `Unsafe.allocateInstance`：丑但有效，离线跑 `ItemStack` 的务实解法。

## 五、建议的修复顺序

1. Folia 库存倾倒告警（P0）——**涉及数据丢失，优先**。
2. `beginSweep` 重复播报（P0）——**一眼可见的观感 bug**，改动 1 行。
3. `floor` 默认值（P1）——改 1 个数字。
4. `StashListener` 的 Folia 短路（P1）——加 1 个判断。
5. 注释过期与 README 对齐（P1）——纯文本。
6. MySQL 告警、`Scheduler` 瘦身、`Verify` 的 `try/finally`（不阻塞发布）。
