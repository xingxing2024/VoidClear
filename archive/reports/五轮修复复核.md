## 三、本轮改对的地方

- `render`（`TrashListener.java:382-401`）先把整页解码到临时数组，全部成功后才 `setContents` 并发布 `entries`；失败时菜单永久失效，旧页面不被半更新。直接 `render` 的故障探针确实覆盖了“解码失败不发布”的关键点。
- `deliver`（`TrashListener.java:189-202`）在背包、副手、光标或掉落物写入失败时立即停止，锁定菜单并记录 UUID、页码、`storageAccepted`，不自动重试。`commit` 在 `replacePage` 成功后必须先通过 `deliver` 才继续更新页面（`:150-160`），顺序比旧版正确。
- 迁移（`TrashStore.java:118-176`）把物品行和迁移凭据放进同一 SQLite 事务；源文件只在提交后改名；改名失败时凭据阻止重启后重复导入，空箱也不会被旧文件重新填满。非空目标、哈希不一致、源文件读取期间变化都会明确拒绝，不猜测性合并。
- 迁移失败不再关闭或重开当前 store；只读旧 YAML 的 `close()` 不会重写源文件（`TrashStore.java:758-783` 的 `dirty && !saving` 条件）。
- `onDisable` 的每一步都走 `cleanup`（`VoidClearPlugin.java:113-148`），某个菜单关闭任务被拒绝不会跳过后续存储清理；心跳把倒计时维护排到菜单刷新之前（`:155-165`），避免单个菜单故障打断下一轮倒计时。
- `invalidateOpenMenus` 逐个玩家捕获调度拒绝（`TrashListener.java:210-218`），符合“失效标志才是交易防线”的定位。

## 四、仍然存在 / 本轮新发现

### R1｜拖拽交付失败时，Paper 会恢复旧光标，可能和插件已写入的背包/存储重复（低概率、高影响）

**位置**：`TrashListener.java:94-113`（拖拽）、`:126-175`（`commit`）、`:189-202`（`deliver`）

**行为**：拖拽处理先 `setCancelled(true)`，然后 `deliver` 直接改写玩家背包/光标。如果 `applyPlayerTransfer` 在写入背包之后、写入光标或掉落物之前抛异常，`deliver` 捕获并返回 false，`commit` 返回 false，事件**保持取消**。此时 Paper 的取消路径只把光标恢复为拖拽前的物品（`ServerGamePacketListenerImpl` 已核对），不会撤销插件刚写入的背包槽位；如果拖拽的是光标上的物品，就可能出现“背包/垃圾箱已有这份物品，光标又被恢复成完整一份”。

`deliveryfault` 探针直接反射调用 `deliver`，没有经过真实拖拽事件，因此测不到 Paper 这一步恢复。日志虽然写了“请核查背包、光标”，但没有说明 Paper 会主动恢复光标。

**建议**：在真实拖拽事件里注入一次光标/掉落物失败，验证最终总量；或者失败时显式把光标、背包、顶部页面归到一个可解释的状态，并在日志里写明“Paper 可能恢复旧光标”。这不是本轮必须重写的架构问题，但需要补测试和文档，否则“不会自动补发”的表述容易被误解。

### R2｜“渲染异常锁菜单”没有覆盖 `renderButtons` 的两处调用

**位置**：`TrashListener.java:243`（`refreshOpenMenus` 的 `else renderButtons(menu)`）、`:160`（`commit` 里 `renderButtons(menu)`）

`render` 里的 `renderButtons` 在 try 内，但另外两处在 try 外。`renderButtons` 会调 `titleValues` → `itemCount()`，遇到坏物品字节时抛异常：心跳路径只会反复报错，不会把菜单标为失效；`commit` 路径更麻烦——此时页面已经 `replacePage` + `deliver`，异常让事件保持取消，又回到 R1 的 Paper 恢复光标问题。建议把整条渲染链路（含 `titleValues`）统一包进同一个失效处理，或让 `itemCount` 对坏行返回安全值并单独报警。

### R3｜坏物品字节仍不在启动/迁移时校验，新探针没有覆盖真实入口（中，运维）

**位置**：`TrashStore.java:223-269`（`loadDatabase` / `load` 仍只查非空、容量、总量）、`TrashStore.java:134-140`（迁移只复制字节，不反序列化）、`TrashListener.java:431`（`itemCount`）

`/vc trash` 的真实入口是 `openPage` → `new Menu(..., titleValues(page))` → `itemCount()`（`TrashListener.java:225-232`），坏行会在 `render` **之前**就抛出，菜单根本打不开；`/vc status` 和 PAPI 也一样。`renderfault` 探针用反射构造 `Menu`（`Map.of()`）并直接调用 `render`，绕过了 `titleValues`，所以它验证的是“打开之后页面损坏”的路径，不是“启动后打不开箱子/查不了状态”的路径。

迁移测试更直接：`TrashSqliteCheck` 用的 `AQ==` / `{1,2,3}` 本身就是无法反序列化的字节，`migrateLegacy` 会照常导入并写凭据；之后这个箱子的菜单/状态/PAPI 会坏。README 第 147 行“异常或超限数据库记录现在会导致启动明确失败”对这类记录仍不成立。

**建议**：加载和迁移时逐条 `deserializeBytes`（失败带 id 报错，或隔离坏行）；把探针改成走真实的 `openPage`/`/vc status` 入口；同时修正 README 的表述。这个问题不修，R1/R2 的坏数据触发条件也一直存在。

### R4｜升级边界：旧版改名失败会硬性拒绝启动（已知取舍，但需文档更醒目）

reviewed4 迁移改名失败会留下“非空 bin.db + trash.yml + 无凭据”。reviewed5 按设计拒绝启动，这比猜测性合并安全，但对管理员是一次停机排障。README 第 5-7 行已经写了处理步骤，这是正确的；建议在升级公告里单独列一条，并确认第 53 行仍写着“当前最新交付 reviewed4”——它和第 3 行的 reviewed5 矛盾，容易让管理员拿旧包或按旧说明操作。

### R5｜`period <= 0` 仍被夹成 1 秒（配置安全，未改）

`Sections.java:38-40, 54-56` 仍是 `Math.max(1, ...)`；`ConfigCheck.java:58-59` 仍把 `trash.clear.period = 0 → 1` 当作期望。`trash.clear.period: 0` 会每秒永久清空垃圾箱，`timer.period: 0` 会每秒扫一轮。上一轮已提，本轮未处理。

### R6｜性能上限未变（已承认，但不该淡出待办）

- MySQL 同步全箱事务 + 共用 store 锁（`TrashStore.java:462-534`）。
- `deposit` 每个掉落实体复制整张 map 并逐堆反序列化（`:295-348`）。
- `itemCount` 反序列化全箱，且每次存入清缓存（`:276-281`）。
- SQLite 每次 flush 全表 `DELETE + INSERT`（`:625-670`）。
- `pageContents` 仍是无界按页缓存（`TrashListener.java:33,159`），只有换菜单/清空才释放；大箱子操作很多页后会长期占内存。这一条不在 `五轮修复记录.md` 的“尚未解决”清单里，建议补进去。

### R7｜小项

- `/vc history player` 仍接受但没有写入方；README 已注明，建议删除或补审计。
- Paper 上 `sweep.batch` 的整批区块仍在一个 tick 内同步跑完（`Scheduler.java:210-248` + `Sweeper.java:169-194`），默认 600 是尖峰不是分帧。
- 窗口外点击（`rawSlot = -999`）仍不会丢掉光标物品。
- `LifecycleCheck` 只测了静态 `cleanup`，没有覆盖真实 `onDisable` 顺序和 `invalidateOpenMenus` 逐个玩家的拒绝路径。
- `交付/` 仍是旧文件；README 第 246/248 行还保留 reviewed/reviewed2 的“最终交付”旧段落。
- `pom.xml` 编译 1.21.11-SNAPSHOT，README 第 10 行仍写 1.21.4+，最低版本没有实服覆盖。
