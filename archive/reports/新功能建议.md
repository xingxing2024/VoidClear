# SweepGuard 新功能建议（历史归档）

> 以下建议基于已移除的回收箱版本，不是当前 VoidClear 的开发计划。
> 保留原文供追溯，不据此重新引入库存、数据库或 GUI。

> 基于当前代码（2026-11-05，约 7900 行，含 Folia `PacketMirror` 协议镜像与 mineflayer 回归脚本）提出。
> 每条都注明：**解决什么、怎么做、代价、建议优先级**。
> 原则：优先做“用现有结构就能接上”的功能，避免为了新功能引入新的线程面或新的丢件路径。

---

## 优先级总览

| # | 功能 | 价值 | 工作量 | 风险 | 建议 |
|---|------|------|--------|------|------|
| 1 | 掉落物**来源追溯**与「谁的东西」 | 高 | 中 | 低 | 先做 |
| 2 | 拾遗站**保留时长 + 到期提醒** | 高 | 低 | 低 | 先做 |
| 3 | `/sg find <物品>` 站内搜索 | 中高 | 中 | 低 | 先做 |
| 4 | 清扫**水位线**（按实体数自适应清理） | 中高 | 中 | 中 | 其次 |
| 5 | 拾遗站**容量上限 + 溢出策略** | 高 | 中 | 中 | 其次 |
| 6 | **按世界/区域**的独立拾遗站 | 中 | 高 | 中高 | 想清楚再做 |
| 7 | 清扫**前后快照对比**（回归 `/sg sweep --dry-run`） | 中 | 低 | 低 | 顺手做 |

## 1. 掉落物来源追溯与「谁的东西」（建议先做）

### 问题

现在所有掉落物一视同仁：玩家的、怪的、机器（刷怪塔/农场）的一起收进公共箱子。
服主常问：**“我钻石剑丢了，是不是被扫了？”** —— 目前 `/sg status` 只给总数，
`/sg check item` 还说“仅凭实体 ID 无法判定”。玩家和服主都没法自查。

### 做法

清扫时给每件掉落物打一条**来源备注**（用现有的 `ItemMeta.lore` 或 PDC），
写入拾遗站的物品上：

- 来源世界 + 坐标（取整）
- 清扫轮次的序号（`sweeper.roundId()`，一个递增 long）
- 如果是玩家扔的（能拿到 `Item#getThrower()` 时），记录 thrower UUID

不需要新表，可以把 note 直接写进物品的 PDC（`NamespacedKey(plugin, "origin")`），
物品本身带着信息走，落库、取走都不会丢。

然后：

- `/sg why <玩家名>` → 列出该玩家扔过、还在站内的物品（按 PDC 反查）。
- 取物时界面上物品 lore 顶部自动加一行 `&8来自 world (x, y, z) · 第 N 轮`。
- `stash.yml` 加开关 `origin.show: true`。

### 代价

- `Sweeper.sweep` 里每件掉落物多写一次 PDC；清扫已经在 `remove()` 前 `clone()`，影响很小。
- 需要拿 `Item#getThrower()` —— 只有玩家扔的掉落物有，机器/怪物没有，返回 null 即可。
- 不改线程模型：PDC 写在区块任务里，本来就是正确线程。

### 风险

低。唯一注意：玩家取走后再扔，PDC 会被清掉（原版行为），这正好符合“来源只对拾遗站有效”的语义。

## 2. 拾遗站保留时长 + 到期提醒（建议先做）

### 问题

现在只有“定时倾倒”一个维度。服主想改成“**物品存 3 天没人领才清**”，
或者“到期前一小时提醒一次”，现有配置做不到——只能整体调 `wipe-period`，
结果是新放进去的东西也跟着一起被倒。

### 做法

给 `Stash` 的每项加一个**入站时间戳**（内存 `long[]` 或 `List<Long>` 与 items 平行；
落库时序列化进 PDC 或单独一列 `created_at`）。

配置新增：

```yaml
stash:
  ttl-hours: 72        # 0 = 不按年龄清
  wipe-warn-minutes: 60
```

倾倒逻辑改成两段：

1. 先清 `now - created > ttl` 的（按年龄）；
2. 再按原来的 `wipe-period` 整体倒。

`/sg status` 多一行“最早一组还剩 X 小时”。

### 代价

- `Stash` 多一个平行数组，`takeInto` / `drain` 要同步维护下标，**这是唯一的复杂度**。
- 落库 `Database` 表结构加一列（SQLite 用 `ALTER TABLE ... ADD COLUMN`，空表或无该列时补）。

### 风险

中。下标同步一旦出错就是错位取物——但 `StashCheck` 已经有现成的断言骨架，
补一组“取中间项后剩余时间戳仍对齐”的测试即可覆盖。

### 更省事的替代方案

不做到期，只做**每项独立倒计时**：物品入站时记 `deadline = now + ttl`，
到期前 10 分钟把它的 lore 标红（“即将清空”），到期时单独清。
这样不需要动 `drain` 的整体逻辑，只需要在 `beat()` 里扫一遍到期的项。
改动比上面小一半，效果接近。

## 3. `/sg find <物品>` 站内搜索（建议先做）

### 问题

站内 64 页 × 45 格 = 2880 组，玩家找自己的东西基本靠翻页。
`mineflayer` 回归脚本里都已经在手工数页了。

### 做法

`CommandHandler` 加一个子指令：

```
/sg find <物品id|名称关键字>
```

实现：遍历 `stash.snapshot()`，按 `Material` 匹配，返回“第 X 页第 Y 格，共 Z 组”，
并给玩家一个**点击就能跳过去**的可点击文本（`ClickEvent` 到 `/sg open --page N`）。

`/sg open` 加一个可选参数 `--page N`（或 `/sg open <页>`），
`StashScreen.open` 已经支持传入 page（`pageByPlayer`），只需把参数透传。

### 代价

- 纯读操作，走 `stash.snapshot()`，不碰锁外的共享状态。
- 翻页参数是已有能力，`open(player, page)` 改成 `open(player, page)` 即可（当前是内部读默认页）。

### 风险

低。唯一注意：`/sg find` 在大库存下要 `snapshot()` 全拷贝一次，2880 组拷贝是毫秒级，可接受。

## 4. 清扫水位线（按实体数自适应清理）

### 问题

现在 `sweep.floor` 是“区块里待清对象少于 N 就整块跳过”，N 是固定的。
实际服里，白天 200 个实体、晚上刷怪塔爆到 2000 个，同一个阈值不适用。
想要的是“**超过上限就多清、没超就少动**”。

### 做法

新增全局水位线：

```yaml
sweep:
  high-water: 3000      # 全服已加载实体超过这个数，本轮强制清
  low-water: 1200       # 低于这个数，只按 floor 正常节奏走
```

`Sweeper.expand` 拿到区块列表后，先统计**总实体数**（`chunk.getEntities().length` 求和，
一次 O(区块数) 的保守估算，不必精确到实体类型），
然后决定本轮是否有必要“清空式”清扫——把 `floor` 临时设为 0。

### 代价

- `collect()` 已经是全量遍历，加一次长度求和不增加复杂度。
- 不影响分批派发，只影响每个区块的 `floor` 判断。

### 风险

中。`getEntities().length` 在 Folia 上每块都要自己的区域线程读——
注意**不要在 `expand`（全局线程）里读实体**，只能在 `sweep()`（区块线程）里累加。
所以更稳的做法是：`sweep()` 里把本块实体数汇报给一个 `AtomicInteger`，
`issue()` 派下一批时读上一批的累计值决定是否降 `floor`。这样多一步间接，但不跨线程。

## 5. 拾遗站容量上限 + 溢出策略

### 问题

`pages-max: 64` 是**界面容量**，不是**存储容量**。库存可以无限增长，
大到超过 `pages-max × 物品格` 时，多出来的物品在界面上根本看不到，也取不到
（`StashScreen.ceilingPages` 只显示到上限，超出部分是“藏起来”）。
README 里没提这一点，服主会以为“64 页 = 2880 组封顶”。

### 做法

1. 真正的容量上限：`stash.capacity: 2880`（组），超出时**拒收**新掉落物
   （掉落物留在地上，不清扫），或**转给下一个策略**。
2. `/sg status` 显示“容量 2880，已用 2750（95%）”。
3. 容量快满时（>90%）广播提醒，并在清扫时**跳过掉落物**只清实体。

### 代价

- `Stash.accept` 加一个容量判断；`Sweeper.sweep` 在 `accept` 前问 `stash.hasRoom(n)`。
- 需要一个“拒收时把物品丢回地上”的出口——但物品已经 `remove()` 了，必须**在 remove 之前**判断。

### 风险

中高。这是**新引入的丢件路径**：如果判断和 `remove()` 的顺序写错，物品会被清掉且不进站。
建议：`accept` 返回实际接收数，`sweep` 只 `remove()` 实际接收了的那些。
这条一定要配 `SweeperCheck` 的新测试。

### 更省事的替代

不做拒收，只做**可见性修正**：`ceilingPages` 超过 `pages-max` 时，
在界面标题里显示“还有 N 组未显示”，并给 `/sg status` 加一行。
这解决了“服主不知道”的问题，不用动接受逻辑，风险几乎为零。

## 6. 按世界/区域独立拾遗站

### 问题

所有世界共用一个大箱子。生存服 + 资源服 + 副本世界混在一起，
玩家在副本里丢的东西跑到主城箱子里，体验很差。

### 做法

`stash.yml` / `config.yml` 增加：

```yaml
stash:
  per-world: true
```

`Stash` 从单一列表变成 `Map<String, List<ItemStack>>`（按世界名分组），
界面按玩家当前世界取对应分组。

### 代价

- `Stash` 的所有方法都要加“当前世界”参数，改动面**覆盖整个 stash 包**。
- 落库表加一列 `world`。
- `StashScreen`、`StashListener`、`PacketMirror` 都要跟着改（`PacketMirror` 只认 `Inventory`，不用动）。

### 风险

中高。这是本次建议里改动面最大的一条，会碰 `takeInto` 的序号核对逻辑（每个分组独立 revision？还是全局？）。
**建议想清楚再做，不要为了“支持多世界”重写整个库存层。**
更省事的做法：只按世界分**倾倒时刻**，不分箱子。

## 7. 清扫前后快照对比 / `--dry-run`

### 问题

`sweep.floor` 到底有没有生效、这轮清了多少、清了什么类型，目前只有一个总数（`/sg status` 的 `last`）。
想验证规则改动前，最好能“预演一次”。

### 做法

`/sg sweep --dry-run`：跑同一套 `collect + 判定`，但**不 remove、不进站**，
只统计“将清理的实体数 / 掉落物组数 / 按类型 Top 10”，发回给执行者。

实现：`Sweeper.start` 加一个 `boolean dryRun`，`sweep()` 里如果 dryRun 就只计数不动作。
`settle()`/`complete()` 不变。

### 代价

- `Sweeper` 加一个字段和 2 个 `if`。
- 结果报告需要一个 `Map<String,Integer>` 按类型累计，在 `tally` 锁里维护。

### 风险

低。是**只读路径**，最坏情况是统计不准，不会动东西。很适合作为第一个“新指令类”功能。

## 8. 拾遗站界面筛选/排序

### 问题

物品按 `tidy-by` 排好后，玩家仍要在 45 格里逐格看。没有“按时间”“按类型”的快捷筛选。

### 做法

`menu/stash.yml` 增加两个图标动作：`sort-next`（切换 `group/count/label/time`）、
`filter`（只显示某类，比如“只看附魔”）。

`Act` 枚举加两个成员，`StashScreen.draw` 里按当前排序/筛选重排 `content.items()`（内存里做，不改库存）。

### 代价

- `Act` 枚举 + `draw` 的排序逻辑，纯内存，不动 `Stash`。
- 排序状态按玩家存在 `pageByPlayer` 旁边。

### 风险

低。唯一注意：`sort` 是**显示层**的排序，不能影响库存真实顺序，否则 `takeInto` 的 index 语义会乱。
所以必须放在 `draw` 里对 `Snapshot.items` 的副本做，不要碰 `Stash.items`。

## 9. 通知渠道（Discord / Webhook）

### 问题

服主不在线时，清扫/倾倒/错误（落库失败、容量满）没有渠道知道。

### 做法

`config.yml` 增加：

```yaml
notify:
  webhook: ''
  events: [wipe, sweep-done, db-error, capacity]
```

`SweepGuardPlugin` 里加一个 `Notifier`，用 `Bukkit.getScheduler().runTaskAsynchronously` 发 HTTP。
只在 `db-error`、`capacity` 这类低频事件上触发，**不要每轮清扫都发**。

### 代价

一个 HTTP 客户端（`java.net.http.HttpClient`，JDK 自带，不用新依赖）。

### 风险

低，但要**确保不阻塞主线程**（异步发送），且失败时只记日志、不重试风暴。

## 10. `/sg why`（判定解释的“实体版”）

### 问题

`/sg check <实体id>` 是按**类型**判定，回答不了“**这一只**苦力怕为什么没被扫”。
比如它带了 `keep` 标记、被别的插件命名了、或者在 `world.creatures: false` 的世界。

### 做法

`/sg why`（不带参数）：对准的实体 → 输出逐条判定结果：
`Tags.has → false`、`named → "Bob"`、`world.creatures → true`、`keep list 命中 → no`、`sweep list 命中 → monster`。
复用 `Decide` 的 `Outcome.reason()`，把它从“一行字符串”变成“多行明细”。

### 代价

`Decide` 加一个 `explain(Entity)` 返回 `List<String>`，与 `sweeps()` 共用同一套分支。
不改判定逻辑。

### 风险

低。注意只读，不要顺手改成“顺便把判定缓存下来”。

## 落地建议

如果只做 3 件事，我建议：

1. **#7 `--dry-run`**（1 天，风险最低，立刻能验证规则改动）
2. **#2 保留时长（简化版：每项独立 deadline + 到期标红）**（2–3 天，直接解决“新东西被旧东西连累倒掉”）
3. **#1 来源追溯**（2–3 天，解决“我的东西去哪了”这个最高频的服主投诉）

其余功能都建立在这三条之上，或者可以等前三条的反馈再决定。

**不建议现在做**：#6 按世界分站（改动面太大，会动摇 `Stash` 的序号核对模型），
除非有明确的多世界分站需求。
